# llm-ferry v1.42.2 — Codex subagents get their task on OpenRouter lanes

A Codex subagent spawned on a lane that falls back to OpenRouter now receives its task instead of an empty message.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/main/README.md)

## Fixed

- **Codex subagents no longer start with an empty task.** Codex CLI 0.159 passes a subagent its task as an `agent_message` input item. The task text is plaintext, but it sits in a content part typed `encrypted_content`. litellm sends OpenRouter deployments straight to OpenRouter's Responses API, which drops that part. The subagent saw only `Payload:` with nothing after it, explored the filesystem looking for its task, and the parent's `wait_agent` timed out repeatedly. The front door now retypes that part to `input_text` on `/v1/responses`. `encrypted_content` on `reasoning` items is left alone.

## Notes

- Pick up the fix on a host with `ferry reload`. Clients need nothing.
- Measured on the identical captured request against OpenRouter Gemini Flash: 0 of 4 runs answered verbatim, 4 of 4 after the retype. End to end, a `heavy` Codex parent spawning a `light` child went from about 20 wasted child turns to an answer 4 s after the spawn.
- The rewrite applies to every `/v1/responses` request, whatever the lane, and fails open: on any error the original bytes go upstream.

## Tests

`lib/ferry-front.test.py` (`TestAgentMessagePayload`, 11 tests) covers the captured item, reasoning items untouched, byte-for-byte passthrough when there is nothing to rewrite, malformed shapes, chat paths untouched, and the end-to-end middleware body with its updated content-length.
