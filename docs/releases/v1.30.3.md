# llm-ferry v1.30.3 — The Goal Plugin's Sidebar Panel Actually Loads

`ferry opencode` now points `tui.json` at a **colon-free, ferry-managed copy** of the goal plugin instead of the tarball spec, because OpenCode cannot load a TUI plugin from any cache path that contains a `:` — which is every path a URL or `github:` spec produces.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/v1.30.3/README.md)

## What v1.30.1 mirrored into `tui.json` never loaded

v1.30.1 fixed the *server* half of the plugin (the `/goal` command and the auto-continue loop) by writing the named tarball spec, and mirrored the same spec into `~/.config/opencode/tui.json` so the *TUI* half — the sidebar "Goal" panel — would load too. The server half works. The TUI half never did, and nothing said so: OpenCode reports a TUI plugin failure through `console.error`, which the terminal UI captures into its own console overlay (`ctrl+p` → "Toggle console"), not to stderr and not to `opencode.log`.

Open that overlay on a v1.30.1 or v1.30.2 client and the entry reads:

```
ResolveMessage: Cannot find package 'solid-js' from '…/packages/opencode-goal-plugin@https:/github.com/…/v0.10.1.tar.gz/node_modules/opencode-goal-plugin/dist/goal-tui.js'
```

The mechanism, traced against opencode 1.18.29 and Bun 1.3.14:

1. OpenCode's cache directory for a plugin is the spec string itself, unsanitised on macOS and Linux (`packages/<spec>`), so a tarball spec yields a path containing `https:/`. A `github:` spec yields one containing `github:`.
2. OpenCode's TUI loader shares its own `solid-js` and `@opentui/*` with plugins through a Bun runtime plugin: an `onLoad` hook that rewrites the plugin's bare imports to virtual `opentui:runtime-module:*` modules.
3. Bun's runtime plugin runner splits every module path at the **first colon** into `namespace:path`. A path such as `/…/packages/opencode-goal-plugin@https:/github.com/…` becomes namespace `/…/packages/opencode-goal-plugin@https`, so the `file`-namespace `onLoad` hook never sees the module, the bare `solid-js` import is never rewritten, and native resolution fails against a package that deliberately does not ship `solid-js`.

One factor varied per cell, same bytes every time: a plain path loads, a path with `@` in it loads, a path under `node_modules` loads; a path with `https:/` in it fails, a path with `a:b` in it fails, and the real cache path fails whether named by the spec or by a `file://` URL to it. A registry spec (`name@1.2.3`) would be colon-free and would work, but the plugin is not on npm.

## What changed

- **`tui.json` names a colon-free copy.** After the pre-install lands the package in OpenCode's cache, `ferry opencode` copies the installed package (with its `node_modules`) to `${XDG_DATA_HOME:-~/.local/share}/ferry/opencode-goal-plugin` and writes `file:///…/ferry/opencode-goal-plugin` into `tui.json`. `opencode.json` keeps the tarball spec: the server half loads through ordinary `node_modules` resolution and was never affected.
- **The copy is marked and refreshed.** A `.ferry-goal-plugin` marker inside the copy records the spec, the pinned tag and the package name. Every run refreshes the copy from the cache when the pin moves, and `--no-install` (or a failed pre-install) leaves a previous copy in place rather than writing a `tui.json` entry that points at nothing.
- **`client-cleanup.sh` removes the copy.** It recognises the managed `file://` entry by its marker, removes it from `tui.json` (deleting the file when that was all it held, as before), and deletes the managed directory. A `file://` or path entry **without** the marker is still yours and is still never touched.
- **`--tui-config PATH`, `--no-tui-config`, `--keep-cache` and `--no-install` keep their meaning.** Only the *value* written to `tui.json` changed.

## Update instructions

### 1. Update the host first

From your host `llm-ferry` repository:

```bash
git pull --ff-only
ferry update --host
```

### 2. Update each client

On each client laptop:

```bash
ferry update --client
ferry opencode
```

### 3. Verify

```bash
cat ~/.config/opencode/tui.json
# "plugin": ["file:///Users/you/.local/share/ferry/opencode-goal-plugin"]
cat ~/.local/share/ferry/opencode-goal-plugin/.ferry-goal-plugin
grep -m1 '"version"' ~/.local/share/ferry/opencode-goal-plugin/package.json   # 0.10.1
```

Then open `opencode` in a terminal wider than 120 columns, press `ctrl+p`, choose **Plugins**, and confirm an *External* entry for `opencode-goal-plugin` with the managed path. Run `/goal <objective>` and the **Goal** panel appears in the sidebar under LSP, showing the objective, the turn budget, and the action plan with a ●/◐/○ marker per action.
