# llm-ferry v1.34.0 — VNC through ferry

A locked-down laptop that runs a VNC server can now be watched from anywhere on the LAN with nothing but a browser: `ferry expose-vnc` publishes the screen through the host exactly like `ferry expose` already publishes any other port, and the host's new `ferry serve-vnc` turns that published port into a page a phone can just open.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/v1.34.0/README.md)

## What's new

```bash
# client
ferry expose-vnc [--local PORT] [--as PUBLIC] [--host H] [--port P] [--token T]

# host
ferry serve-vnc [--port P] [--bind ADDR] [--foreground] [--fetch]
```

`ferry expose-vnc` is `ferry expose` with two additions: a preflight that
connects to `127.0.0.1:<local>` (default `5900`) and refuses to publish
anything that doesn't answer with the RFB greeting a VNC server always sends
first, and a `"kind": "vnc"` tag on the relay registration so the host can
tell a screen from an ordinary tunnel. `ferry serve-vnc` is a new host-only
daemon on port `8099` that reads the relay's own state file, lists every
currently published `vnc` port on its index page, and serves each one as a
noVNC browser viewer. `--fetch` downloads the pinned noVNC 1.7.0 release
(checksum-verified) into `~/.config/ferry/novnc/` — required once before the
viewer will start.

## How the bytes move

```
phone browser ──http──▶ host:8099 /vnc/5900  (noVNC page)
phone browser ──ws────▶ host:8099 /ws/5900 ──tcp──▶ host:5900 (relay-published)
                                                        │ relay data conn
                                                        ▼
                                              laptop ──▶ 127.0.0.1:5900 (VNC server)
```

The viewer page and the relay's published port are two separate hops: the
browser talks WebSocket to `ferry serve-vnc`, which bridges it to the ordinary
`ferry relay` TCP port that `ferry expose-vnc` already publishes. `/ws/<port>`
checks the relay's state file **at the moment of the request** — a port has
to be present there with `kind: vnc` or the bridge answers `403`, so a screen
that stops being published stops being reachable immediately, not just on the
next poll.

## Security

The relay token authenticates the client that *registers* the screen, the
same as any other `ferry expose`; it says nothing about who reaches the
screen afterward, so the VNC server's own password is what actually gates
access. `ferry serve-vnc` serves plain HTTP on the LAN by default, like every
other ferry port — pass `--bind 127.0.0.1` to keep the viewer local to the
host. Ferry's own ports remain refused as publish targets, so `expose-vnc`
can't be pointed at the endpoint or the relay itself.

## Tests

`lib/ferry-vnc.test.py` exercises the bridge as a real process over real
sockets: the WebSocket handshake (`Sec-WebSocket-Accept`, a missing key →
400), framing round-trips at all three payload-length encodings with masked
input and unmasked output, ping/pong and the close handshake, port gating
(absent, `kind: tcp`, and `kind: vnc` cases), the index page, static serving
with a path-traversal check, and noVNC extraction against both a correct and
a mismatched checksum. `lib/ferry-relay.test.py` gained coverage for
`expose-vnc`: it refuses a local service that doesn't greet RFB, publishes
when one does, and the state file records `kind: vnc` there and `kind: tcp`
for a plain `expose`.
