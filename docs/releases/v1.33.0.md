# llm-ferry v1.33.0 — Promote a Client into a Host

A machine that has been a **client** of someone else's ferry can now become a **host** of its own with one command: `ferry migrate`. It is the reverse of `client-bootstrap.sh` — where that wires a laptop to point at some other machine's endpoint, this turns the laptop into the endpoint.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/v1.33.0/README.md)

## What's new

```bash
ferry migrate --dry-run   # print every step, change nothing (run this first)
ferry migrate             # do it (asks once before it starts)
ferry migrate --full      # ...and reload the GPU lanes at the end
```

Two pieces ship together: the `ferry migrate` command (`lib/ferry-migrate.zsh`) and the migration engine it drives, [`client-to-host.sh`](../../client-to-host.sh).

## Why it needs two pieces

A client's `ferry` is a single downloaded file in `~/.local/bin` with no repository behind it — but becoming a host needs the whole checkout (`host-reset.sh`, the route template, `lib/`, `ferry install`). So `ferry migrate` owns exactly one job: make sure a checkout exists — the one this CLI already lives in, or one it clones to `--dir` (default `~/gdev/llm-ferry`, else `~/llm-ferry`, override with `--repo`) — and then hand off. All the transition logic lives in `client-to-host.sh`, the single source of truth, the same way `ferry update` delegates to `host-reset.sh` / `client-reset.sh` rather than re-implementing either. Run the engine directly if you already have the repo.

## What the engine does, in order

1. **Confirm this machine is a client.** ferry decides host-vs-client purely on `~/.config/ferry/client.json` (`CLIENT_MODE` in `lib/ferry-core.zsh`); no file means nothing to migrate.
2. **Carry the master key forward.** If the client profile holds a front-door key, it is written to `~/.config/ferry/secrets.env` as `LITELLM_MASTER_KEY` (a key already there wins; the value is never printed).
3. **Seed the route config** from `litellm-route-example.yaml` if `~/.config/ferry/litellm.yaml` is absent — `host-reset.sh` requires it to exist.
4. **Provision dependencies via `ferry install`** from the checkout, deliberately not `host-bootstrap.sh`: `ferry install` is OS-aware (uv + litellm everywhere; mlx-vlm and the ~16.6GB default models on macOS only, skipped on Linux), installs the host's own shell wrappers pointed at `127.0.0.1`, and symlinks `ferry` into the checkout.
5. **Archive `client.json`** to `client.json.pre-migrate.<UTC>`. That single move is the pivot that leaves `CLIENT_MODE`, and it is reversible.
6. **Bring the host online via `host-reset.sh`:** validate the route config, re-link the CLI, bounce the proxy and share server, re-wire opencode/claude at `127.0.0.1`, and verify the lanes.
7. **Re-key the host's own tools.** `host-reset` resolves the opencode/claude bearer from the `client.json` step 5 archived, so on a keyed front door it would bake the `local` placeholder and every local request would 401. The engine reads the key back and re-applies the opencode + claude wiring with it. Keyless hosts skip this step.

## Reversible, and resumable

Going back is one move: `mv ~/.config/ferry/client.json.pre-migrate.<UTC> ~/.config/ferry/client.json` makes the machine a client again. The archive happens **after** the dependency install and **before** the reset, so a failed install leaves a recoverable client and `host-reset.sh` never sees the `client.json` it refuses to run beside. If a run stops between the archive and a healthy endpoint, re-running `ferry migrate` reports the box already left client mode and points at `host-reset.sh` to finish rather than migrating from scratch.

## Operator notes

- On macOS the dependency step downloads ~16.6GB of default models; the confirmation prompt and `--dry-run` both say so up front.
- `--dry-run` changes nothing, prints every action, and does not require the machine to be a client — run it first to preview.
- `--pull` opts into `host-reset`'s `git pull --ff-only`; the default is `--no-pull` so a dirty or diverged checkout is never touched.
- The command is documented under "Promoting a client into a host" in the README.
