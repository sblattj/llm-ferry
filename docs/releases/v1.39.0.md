# llm-ferry v1.39.0 — per-device keys

Every client can now hold its own key instead of the shared master key.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/main/README.md)

## What's new

- **Device keys, automatically.** Run `client-bootstrap.sh` with the master
  key and a v1.39.0 host mints a key for that machine
  (`POST /v1/ferry/keys/enroll`); the client stores only `api_key`, never the
  master. Re-running the bootstrap against the same host rotates the key
  under the same name.
- **`ferry keys add | list | revoke | set`** on the host. A new key is printed
  once, alone on stdout; only its sha256 is stored in
  `~/.config/ferry/keys.json` (0600). A revoke takes effect on the next
  request with no restart. `master` and `host` are reserved names.
- **Client routes only.** A device key works on inference
  (`/v1/chat/completions`, `/v1/completions`, `/v1/messages` and
  `count_tokens`, `/v1/responses`, `/v1/embeddings`), the model lists,
  realtime, Gemini-native generate, `/v1/ferry/fleet` and the health probe.
  Every other route, litellm's admin API and UI included, answers 403
  `route_not_allowed`, so a device key cannot reach audio, images, files or
  batches. The master key is unaffected.
- **Optional limits per key:** allowed lanes (403 otherwise), requests per
  minute and a monthly token budget (429 with `Retry-After`; the budget
  answers `insufficient_quota`). Budgets count input + output tokens per
  calendar month (UTC); there are no USD budgets in this release.
- **Metering.** Tokens are charged once per request, off the event loop,
  when the response completes — streams included, and the charge survives a
  client disconnect. For legacy `/v1/completions` streams the front asks
  litellm for usage (`include_usage`).
- **Attribution.** A device key's name is its fleet identity, every event
  record carries `key`, and `ferry dash` gains a Device keys card and
  per-key labels in the live feed.

## Notes

- Existing clients keep working on the master key; only re-running the
  bootstrap moves one to a device key. `ferry update` never touches
  credentials.
- Fail-closed: a corrupt `keys.json` refuses device keys (401) and an unusable
  usage DB refuses them (503); the master key is unaffected by either.
- Tokens are charged when a response completes, so every request already in
  flight when a budget runs out may still finish: the overshoot can be more
  than one request.
- Limits and metering apply on the OpenAI- and Anthropic-style inference
  routes. Gemini-native generate (`/v1beta/models/…`) and the websocket
  routes (`/v1/realtime`) authenticate a device key but carry no lane, RPM or
  budget accounting.
- A device key sent as `?key=` is removed from the URL before forwarding (the
  master travels in the `x-litellm-api-key` header), so no key is written to
  the access log. Two different credentials alongside an `fk-` key get a 401.
- The enroll endpoint is master-only, refuses bodies over 64 KiB (413) and
  answers with `Cache-Control: no-store`. On a host with **no master key**,
  enrollment is allowed from loopback only — and under `tailscale serve` a
  tailnet peer arrives as loopback, so it can enroll.
- The front door must be restarted once (`ferry reload`) to load the new
  code. A client needs the v1.39.0 `ferry` to read `api_key`; re-running the
  bootstrap installs it.
- `client-to-host.sh` never promotes a device key to a new host's master key.
