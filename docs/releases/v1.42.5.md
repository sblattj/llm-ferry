# llm-ferry v1.42.5 — Codex heavy runs on Kimi K3 again

Codex requests to the domestic `heavy` lane are served by its Kimi K3 primary again, instead of failing over to GLM on every call.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/main/README.md)

## Fixed

- **The anthropic-adapter deployment (Kimi K3) no longer rejects Codex requests.** Codex CLI sends a `tool_search` tool with every Responses request. LiteLLM's own `anthropic/` adapter raises `Unsupported tool type: tool_search` before the request reaches the network, so every Codex call on `domestic.heavy` (`anthropic/k3`) fell back to `domestic.heavy-glm`. ferry's event log recorded no hop error for it. The deployment-level `tool_search` strip from v1.42.3 now covers `anthropic/` deployments as well as z.ai. Other hops still receive the tool.

## Notes

- Pick it up on a host with `ferry reload`. Clients need nothing.
- Verified live with a captured Codex request on `heavy` and fallbacks disabled. Before the fix, the request returned 500, and only removing `tool_search` made it succeed. Removing `web_search` or `namespace` changed nothing. After the fix, all variants returned 200 from `kimi-k3-dom-heavy`. A full `ach run --agent codex` on the domestic fleet spawned a `light` subagent: every `heavy` call hit K3 with 0 fallbacks, and the subagent ran on `domestic.flash`.

## Tests

`lib/ferry-front.test.py` (`TestZaiToolSearchStrip.test_anthropic_adapter_drops_tool_search`): `tool_search` is removed for `anthropic/` models and for `custom_llm_provider: anthropic`, and other tools are kept.
