# llm-ferry v1.36.0 — the extraction lane comes home

The `schematron` HTML→JSON lane now runs **on the host GPU**. `ferry up` launches a third `mlx_vlm.server` — Schematron-8B at 8-bit MLX, on internal port `8100` — and the `schematron` deployment fronts it instead of OpenRouter. The cloud extractor is still there, under a new name, and nothing falls back to it.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/main/README.md)

## What's new

```bash
# host
ferry up                     # the stack: now eight lanes, three of them on the GPU
ferry up --schematron        # the extraction door (8094) + its local backend (8100)
ferry up --local-schematron  # the MLX backend alone, raw, no litellm in front
```

| Lane | Was | Is |
|---|---|---|
| `schematron` | `openrouter/inference-net/schematron-v2-turbo` | `openai/pchamart/schematron8B-mlx-8bit` on `127.0.0.1:8100` |
| `schematron-cloud` | — | `openrouter/inference-net/schematron-v2-turbo` (new lane, same deployment) |

The model is [`pchamart/schematron8B-mlx-8bit`](https://huggingface.co/pchamart/schematron8B-mlx-8bit), an 8-bit MLX quant of `inference-net/Schematron-8B` — a llama-arch fine-tune of Llama-3.1-8B specialised for structured extraction. ~8.5 GB resident, 32 layers, GQA with 8 KV heads × 128 head dim, 128k context.

## No fallback between the two, on purpose

`schematron` does **not** fall back to `schematron-cloud`. Both carry an empty `fallbacks` entry. Two reasons, and they compound:

- **A local lane that silently ships the page off-box defeats the point of asking for it.** This is the same doctrine `local-orch` and `local-sub` have always run under: a dead GPU lane surfaces as an error, never as a quiet cloud spend.
- **No silent model swap behind a schema-pinned consumer.** Schematron-8B and schematron-v2-turbo are different models with different extraction behaviour. A caller that pinned a `json_schema` to one must not be swapped onto the other mid-flight and handed subtly different output.

A caller that wants the cloud extractor — host GPU busy, a page too large, an A/B between the two — asks for `schematron-cloud` by name.

## The KV governor for this lane

`LOCAL_SCHEMATRON_KV_BITS` is empty: the KV cache stays **unquantized**. The arithmetic is why that is affordable — 32 layers × 8 kv heads × 128 head dim × 2 (K and V) × 2 bytes = **131 KB/token**, so even a full 128k stream is ~17 GB worst case, and a realistic single-page extraction is a small fraction of it. Quantizing would buy little and cost fidelity on a lane whose entire job is copying verbatim out of the prompt.

`LOCAL_SCHEMATRON_MAX_SEQS` defaults to **2**, not 4. This lane's prompts are whole HTML pages: deep prefill, shallow decode. Admitting many concurrent extractions grows KV far faster than it grows throughput. `LOCAL_SCHEMATRON_MAX_KV` is the model's full `131072`.

Running all three GPU lanes keeps ~42 GB of weights resident before any KV cache. Watch it with `ferry status`, which now labels `8100` as `local-schematron lane (internal)` and reports its `phys_footprint` and loaded model like the other two.

## The prompt contract is the client's job

Schematron expects the JSON schema **inside the user message** — system `You are a helpful assistant`, then a user turn shaped `You are going to be given a JSON schema ... The schema is as follows:\n\n<schema>\n\nHere is the HTML page:\n\n<html>\n\nMAKE SURE ITS VALID JSON.` ferry fronts the model verbatim and rewrites no prompts; cdp-toolkit's `extract_page` is the caller that builds that shape.

## Lifecycle

**The door reuses a warm lane, it does not reap it.** `ferry up --schematron` and plain `ferry up` wire the same deployment to the same `:8100`. If that port already answers `/v1/models` with a 200, the door fronts the running process and says so in its banner; only a cold port gets a fresh launch. Killing a lane the main stack is serving through would be a silent outage on a door the operator never touched.

**`ferry down --port 8094` stops the backend too — but only when the stack is down.** With `:8090` listening, the companion door is the borrower, not the owner, and leaves `:8100` alone. With no stack, the door owns the lane and takes it down rather than stranding 8.5 GB of weights.

Plain `ferry down` is unchanged in shape: one `pkill -f mlx_vlm.server` already covered every lane, and `8100` joins the belt-and-braces port loop behind it. The relay's reserved-port list claims `8100` so a client exposure can never be handed it.

**Why 8100 and not a gap in 8090-8099:** that block is full — `8090` front, `8091` dash, `8092`/`8093` the older MLX lanes, `8094` the schematron door, `8095` share, `8096` HF, `8097` proxy, `8098` relay, `8099` VNC. The ferry range continues upward rather than reaching below the front door. Override with `FERRY_LOCAL_SCHEMATRON_PORT`.

## The comment that said this was impossible

`litellm-route-example.yaml` carried a block headed *"LOCAL-FIRST WAS NOT EXPRESSIBLE HERE (checked 2026-09-12)"*. It was right at the time and for the right reason: a route config can only **front** an MLX server, never conjure one, and `ferry up` launched exactly two. It also named the fix — *"teaching ferry-serve.zsh a third MLX lane — not a config edit."* That is this release; the comment has been rewritten to describe the wiring that now exists.

## Tests

`lib/ferry-serve.test.py` grew `TestLocalSchematronLane`, reading the generated `ferry`: the stack launches **three** `_ferry_launch_mlx` calls including `local-schematron`, frees and waits on `$LOCAL_SCHEMATRON_PORT` at 900 s, the `--schematron` door launches the lane behind its litellm front and probes the warm port before deciding, `cmd_down`'s port loop and the relay's reserved list both carry the port, `cmd_status` labels it, and the `--local-schematron` solo mode parses.

`TestSchematronFilter` now asserts the filtered door's upstream is `openai/pchamart/schematron8B-mlx-8bit`, and `TestRouteExampleSchematron` loads the shipped template with PyYAML to pin the split: `schematron` points at the loopback port, `schematron-cloud` is the OpenRouter deployment, both are `public`, and **no fallback entry maps `schematron` to `schematron-cloud`**.
