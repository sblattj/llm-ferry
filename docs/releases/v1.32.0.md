# llm-ferry v1.32.0 — OpenCode Learns How to Use the Goal Plugin, and the Plugin Learns to Run All Day

`ferry opencode` now installs an OpenCode skill, `using-the-goal-plugin`, that teaches the model how to actually drive the bundled goal plugin instead of just reacting to what it injects each turn.

The plugin itself moves from **v0.10.1 to v0.11.0** in the same release: unattended goals get unlimited turns, an eight-hour window and a real token budget, and the two brakes that pause a run stop misreading working turns as idle chatter.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/v1.32.0/README.md)

## What the model never knew

The goal plugin re-injects its own state into the prompt on every turn — a `<goal_plan>` block with the recorded action plan and its per-action status, a `<progress_budget>` reading once the turn/minute/token window opens, a `<budget_wrapup>` warning as it closes, and an `<evidence_required>` nudge after a rejected completion — and it enforces a strict completion grammar: a `[goal:complete]` line is only honored when it's immediately preceded by a `[goal:evidence] <proof>` line substantiating it. None of that is explained anywhere the model reads. It knows the shape of the blocks because it sees them, but not the contract behind them: how big a plan should be before calling `goal_plan_set`, what actually counts as evidence under a Claim → Evidence → Verdict rule versus a bare assertion, that a real (human) user message arriving mid-loop pauses auto-continue and a `/goal` control turn (status, pause, resume) is read-only and should not itself be treated as progress, or that a rejected `[goal:complete]` means verify-then-restate, not repeat-and-hope.

The gap showed up concretely on the heavy lane: models were stopping on files a previous, unrelated session had left dirty and claiming the goal complete without ever having produced evidence the objective was actually met.

## What changed

- **New skill file.** `opencode/skills/using-the-goal-plugin/SKILL.md` is the source of truth: goal sizing and decomposition, working the plan under Claim → Evidence → Verdict, the exact `[goal:evidence]`/`[goal:complete]` grammar, budgets and pauses, treating `/goal` control turns as read-only, and reading the sidebar panel.
- **Host install.** `ferry opencode` copies it to `$HOME/.config/opencode/skill/using-the-goal-plugin/SKILL.md` in the same run that wires the plugin itself — gated on ferry's own goal entry being the one in play, so `--no-default` and a pre-existing local fork of the plugin skip it — and re-copies it on every such run, so an edit to the repo file reaches an already-wired host on the next one. `ferry install` and `host-reset.sh` copy it too, the latter unconditionally, so a host carrying a local fork still gets the doctrine.
- **Client install.** `client-bootstrap.sh` embeds the same file and writes it to `$HOME/.config/opencode/skills/using-the-goal-plugin/SKILL.md` in the **default** scope only — not on the guardrails switch (a `--no-guardrails` client still gets the skill), but on the opencode scope, because opencode reads skills only from its own global config dir and `--profiles-only` exists to leave `~/.config/opencode` untouched. Both narrow scopes print that the skill was not installed.
- **Cleanup.** `client-cleanup.sh` removes it under both the singular `skill/` and plural `skills/` spellings, the same both-spellings handling the existing `spawning-subagents` guardrail already needs because the two installers disagree on which one they write.
- **Reporting.** The three scripts that drive the takeover (`host-reset.sh`, `client-bootstrap.sh`, `client-reset.sh`) run `ferry opencode` once per config target, and each run is a fresh process, so the skill line would print three to five times for one install — and on a `--profiles-only` client it would promise a file that scope deliberately does not ship. Each script now states the skill's fate once, itself, and passes `FERRY_GOAL_SKILL_QUIET=1` to the runs it drives. That silences the report line only; the copy still happens on every target.
- **Tests.** The client-bootstrap and host-reset suites cover the new skill's install and removal the same way they already cover `spawning-subagents`.
- **Operator note.** The host's dotorg config overlay used to pin `plugin: ["github:sblattj/OpenCode-goal-plugin#v0.9.1"]` and re-render it over ferry's own tarball spec on every refresh; that overlay entry is removed, so ferry now owns `plugin` outright. This is a host-side config change outside this repo, not a code change here.

## The goal plugin moves to v0.11.0

The spec ferry appends to `plugin` — and the ferry-managed copy `tui.json` points at — is now
`opencode-goal-plugin@https://github.com/sblattj/OpenCode-goal-plugin/archive/refs/tags/v0.11.0.tar.gz`.
Ferry's wiring is unchanged; the package on the other end of it is not. The authoritative narrative is
the plugin's own [CHANGELOG 0.11.0 entry](https://github.com/sblattj/OpenCode-goal-plugin/blob/v0.11.0/CHANGELOG.md);
below is what an operator notices.

### What you notice

- **Auto-continue turns are unlimited by default, rendered `∞`.** The old ceiling was 10 turns, and it stopped healthy long runs for no reason. Unlimited is spelled `maxTurns: 0` — zero rather than `Infinity`, because the option round-trips through the persisted goal state and `JSON.stringify(Infinity)` is `null`. `--max-turns` accepts `0`, `unlimited`, `none`, `inf`, `infinite`, `infinity` and `∞`; a positive integer still behaves exactly as before.
- **The wall clock is eight hours, rendered `8h`** (was 15 minutes), and every duration is now truncated rather than rounded: `45s`, `45m`, `1h`, `1.5h`, `8h`. A 20-second budget used to report its limit as `0m`.
- **The 100,000,000-token budget now means cumulative token SPEND**, not the peak size of a single message. Spend is input + output + reasoning + cache read/write summed over every message the goal produced, including work it delegated to a subagent; cache reads are in the sum because they are billed. Under 0.10.x the budget was compared against a peak context size that a model caps at 200k–2M, so the token brake, the token warning and the token half of the wrap-up were dead code on a default goal, and every continuation prompt told the model it had roughly 500× its real headroom.
- **Context pressure gets its own guard.** Peak context is measured separately against `contextWindowTokens`, which defaults to **auto**: the plugin reads the running model's own window from the host's provider catalog. When the host cannot name one there is no context ceiling at all — `/goal status` renders `Peak context: 147,000/∞`, the continuation prompt says `context_remaining: unlimited`, and the guard simply stays off rather than pausing a healthy run against a number nobody verified. `--context-window <n|k|m>` sets it explicitly.
- **The stall brakes judge the whole turn, and talking alone takes ten turns to pause instead of two.** A tool call anywhere in a turn now clears both brakes; the plugin's own `goal_*` calls do not count as work, so a model cannot hold the brake off by calling `goal_plan_set` every turn. The visibility window the turn is reconstructed from widened from 50 messages to 200, and a turn sliced by that window charges neither brake and says so in the history.
- **The wrap-up handoff is reachable again, and it is the real ceiling.** `<budget_wrapup>` now fires at 80% of whichever of spend (80m), peak context (80% of the model's window, when one is known) or the clock (6.4 h) arrives first — and it **pauses** the goal, so the 100% stop reasons (`max tokens reached`, `context window reached`, `max duration reached`) only fire when a single turn jumps from below 80% to the limit. Under 0.10.x the handoff watched only the unreachable token budget, so a default goal would have auto-continued for the full window with no handoff at all.
- **The rendering changes everywhere the goal is shown.** The session title now reads `▶ ship it · 3/∞ · 2m/8h · 45k/100m` — it carries the duration *limit* next to the elapsed clock, which it previously omitted — and the sidebar stats line reads `1/∞ turns · 1m/8h · 147k/100m tokens`, gaining a fourth `147k/1m ctx` stat only when a context ceiling is known. Both halves render through one shared formatter now, so the panel and the title cannot drift apart. `/goal status` gains a `Peak context:` line.
- **The sidebar payload is `metadata.goal` `v: 2`**, with `turns.max` now `number | null`, `durationMs` and `context` beside `minutes`, and `tokens.used` carrying spend. **Upgrade both halves together:** the server half is registered in `opencode.json` and the panel in `tui.json`, and a 0.10.x panel reading a v2 payload silently drops the turns stat. `ferry opencode` installs both from the same pinned copy in one run, so they cannot skew — unless you point `tui.json` at your own fork, which ferry deliberately leaves alone.

### Why the brakes were wrong

OpenCode creates a **new assistant message for every LLM step of one prompt**, so an ordinary turn is N assistant messages sharing one `parentID`: the steps that ran tools, then a separate, text-only closing summary. The no-tool-call and no-progress gates read only the newest of them, so they scored the summary and never saw the tools. Measured against a live OpenCode session database, 33 of 43 turns used tools and in **28 of those 33** the last assistant message was text-only — 28 productive turns charged as tool-free, and a default goal paused after two of them with `Stopped: no tool calls`.

The same one-message reading threw away real completions: when a model wrote its `[goal:evidence]`/`[goal:complete]` block and then made one last tool call, the markers were silently discarded and the goal kept auto-continuing to a budget ceiling. Markers are now read from the turn's last text-bearing step. The marker grammar itself is unchanged — last two non-blank lines, plain and adjacent — which is what the new skill documents.

## Update instructions

### 1. Update the host first

From your host `llm-ferry` repository:

```bash
git pull --ff-only
ferry update --host
ferry opencode
```

That one `ferry opencode` does both halves of this release: it copies the skill, and it rewrites the
`plugin` entry to the v0.11.0 tarball, pre-installs it, refreshes the ferry-managed TUI copy that
`tui.json` points at, and purges the cache directory of the v0.10.1 spec it just migrated away from.
An older spelling — the v0.10.1 tarball, a `github:` ref, the tuple form — is migrated in place; a
local path to your own fork is left alone and gets neither half. **Restart OpenCode afterwards**: the
plugin is loaded at start, so a session already running keeps the old one.

### 2. Update each client

On each client laptop, re-run the **bootstrap**, not `ferry update`:

```bash
curl -fsSL http://your-mac.local:8095/client-bootstrap.sh | zsh
```

The skill ships to clients as a heredoc inside `client-bootstrap.sh`, which is the only
client-side copy of it — a client has no `llm-ferry` checkout, so `ferry opencode` there
says `not installed here (no checkout)` and `client-reset.sh` (what `ferry update --client`
runs) never writes skill files at all — a reset now says exactly that, once, in place of
ferry's per-target line. That is the same bootstrap-only footing the
`spawning-subagents` guardrail has always had. `ferry update --client` still gets the
client a current CLI and configs; it just cannot deliver this file.

The **plugin** half is not bootstrap-only: `client-reset.sh` runs `ferry opencode` once per config
target, so `ferry update --client` does move a client to the v0.11.0 pin, TUI copy included. It is
only the skill file that needs the bootstrap. Restart OpenCode on the client too.

No reload is needed either way — the front door on `:8090` is untouched by this release.

### 3. Verify

```bash
opencode debug skill > /tmp/oc-skills.json   # a pipe truncates at 64 KiB
python3 -c 'import json;print([s["location"] for s in json.load(open("/tmp/oc-skills.json")) if s["name"]=="using-the-goal-plugin"])'
```

Prints the installed path; before v1.32.0 it prints `[]`.

Then, in a session, ask the model to load the `using-the-goal-plugin` skill and quote its first heading.

Both halves of the plugin, which are versioned separately on disk:

```bash
find "${XDG_CACHE_HOME:-$HOME/.cache}/opencode/packages" \
  -path '*/node_modules/opencode-goal-plugin/package.json' -exec grep -m1 '"version"' {} +
grep -m1 '"version"' ~/.local/share/ferry/opencode-goal-plugin/package.json
```

Both must say `0.11.0`. The quickest end-to-end check is to start a goal with no flags and read the
sidebar: v0.11.0 renders `1/∞ turns · 1m/8h · …`. A bounded turn count there means the server half is
still the old plugin, and a stats line with **no** turns stat at all — while the session title looks
right — means the panel half is, since a 0.10.x panel cannot read a v2 payload's turn budget.
