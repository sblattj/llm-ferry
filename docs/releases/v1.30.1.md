# llm-ferry v1.30.1 — Install the Goal Plugin in a Form OpenCode Can Load

`ferry opencode` now writes the OpenCode goal plugin as `opencode-goal-plugin@https://github.com/sblattj/OpenCode-goal-plugin/archive/refs/tags/v0.10.1.tar.gz`, mirrors it into `tui.json` so the sidebar half loads, purges the dead package-cache directories, and pre-installs it through `opencode plugin` so a failure is visible at bootstrap time instead of never.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/v1.30.1/README.md)

## What was wrong with v1.29.4

v1.29.4 pinned `github:sblattj/OpenCode-goal-plugin#v0.9.1` and reported it as installed. On OpenCode 1.18.29 that spec, and every spelling ferry wrote before it, **installed to disk and never loaded once**. Two independent defects, both silent:

- **No npm name.** For a bare `github:owner/repo[#tag]` — or a bare tarball URL — npm-package-arg returns no name, so `npa(pkg).name ?? pkg` (`packages/core/src/npm.ts:119`) yields the *whole raw spec* as the package name. After a completely successful reify, `tree.edgesOut` is empty, so `npm.ts:130-134` falls back to `resolveEntryPoint(<raw spec>)`, which cannot resolve, and throws `NpmInstallFailedError` — **with the package fully written to disk**. The failure is published as a session event and never logged (`plugin/index.ts:198-201` → `:139-141`; the start/missing reporters at `:191-192` are no-ops), the entry is dropped (`loader.ts:234`), and npm-source plugins are never retried (`loader.ts:178`). Nothing reaches `opencode.log`. "The cache directory has files in it" was exactly the wrong evidence: a complete package on disk *is* the failure mode.
- **Git prepare.** Any *git* spec whose `package.json` declares `build`/`prepack`/`prepare`/`install`/`pre|postinstall` makes pacote's `GitFetcher` run a prepare step (`pacote/lib/git.js:160-197`) — arborist's `ignoreScripts: true` does not suppress it. OpenCode derives `npmBin` from `fileURLToPath(new URL("..", import.meta.url))` (`packages/core/src/npm-config.ts:10`), which inside the bun single-file binary is `/$bunfs/bin/npm-cli.js`; because that ends in `.js`, pacote spawns `process.execPath` — OpenCode itself — with it as `argv[1]` (`pacote/lib/util/npm.js:5-7`). The child prints OpenCode's own help, exits 1, and the install dies with `git dep preparation failed`. The plugin has declared `build` + `prepack` since v0.9.1.

Reproduced through the production entry point on 1.18.29:

```
$ opencode plugin 'github:sblattj/OpenCode-goal-plugin#v0.9.1' --global
■  Install failed
■  Could not install "github:sblattj/OpenCode-goal-plugin#v0.9.1"
■  git dep preparation failed                                     → exit 1

$ opencode plugin 'opencode-goal-plugin@https://github.com/.../v0.10.1.tar.gz' --global
Plugin package ready / Detected server + tui targets / Installed …  → exit 0
```

## What changed

- **The canonical spec is name-prefixed and a tarball.** The `name@` prefix gives npm-package-arg a real name, which fixes both the entrypoint resolution and the cache short-circuit. A *remote tarball* is fetched by pacote's `RemoteFetcher`, which never enters the git prepare path — it is immune to the second defect rather than merely dodging its trigger. The tag stays pinned because the spec string **is** OpenCode's cache key.
- **Everything earlier is migrated.** Bare npm name, `@prevalentware/opencode-goal-plugin`, `willytop8/…`, `github:…`, `github:…#ref`, `git+https://…`, plain or name-prefixed tarball URLs, and the `["pkg", {opts}]` tuple form (options preserved) are all rewritten to the canonical spec on every run and de-duplicated to one entry. An exact match is a no-op. A **local filesystem path** to your own fork is still never touched.
- **`tui.json` is written too.** The plugin ships a server half and a TUI half, and OpenCode reads TUI plugins *only* from `tui.json`/`tui.jsonc` — `opencode.json`'s `plugin` array feeds the server loader alone (`packages/opencode/src/config/tui.ts:157-210`). The full takeover now mirrors the same entry into `~/.config/opencode/tui.json`, creating it with `"$schema": "https://opencode.ai/tui.json"` if absent, snapshotting any previous file as `tui.<UTC>.jsonc`, and leaving every other key alone. Without this the `/goal` command works and the sidebar panel silently never appears. New flags: `--tui-config PATH` and `--no-tui-config`. A `--config` outside `~/.config/opencode` (the ferry lane profiles, `--profiles-only`, `--no-opencode`) never creates one.
- **Dead cache directories are purged.** OpenCode never invalidates `~/.cache/opencode/packages` — no TTL, no version comparison, no eviction. Ferry now removes the per-spec directory of every entry it migrated away from, plus the known-dead `github:sblattj/OpenCode-goal-plugin#v0.9.1`, `github:sblattj/OpenCode-goal-plugin`, `github:sblattj/opencode-goal-plugin` and `opencode-goal-plugin@latest`; and it removes the canonical directory itself when that holds an *interrupted* install, because an empty `node_modules/opencode-goal-plugin` is treated as installed forever with no self-heal and no retry. Only directories carrying the package name are ever deleted, and only the exact per-spec directory — never the whole `opencode-goal-plugin@https:` subtree, which every tarball version shares. `--keep-cache` opts out.
- **The plugin is pre-installed and verified.** After the config write, ferry runs `opencode plugin '<spec>' --global` against a throwaway `XDG_CONFIG_HOME`/`XDG_DATA_HOME`/`XDG_STATE_HOME` with `OPENCODE_CONFIG` unset (so its config patch lands in the sandbox) and the **real** `XDG_CACHE_HOME` (so the shared package cache is what gets populated), under a 120-second wall clock. It then checks the cached `package.json` version against the pinned ref and the presence of both `dist/goal-plugin.js` and `dist/goal-tui.js`. Success prints `Plugin: installed opencode-goal-plugin 0.10.1 (ready for next opencode start)`; failure prints a warning with the real error and **still exits 0** — the config was written correctly, and an offline laptop must not fail a bootstrap. `--no-install` skips it, as does a missing `opencode` binary or a config already satisfied by a local fork.
- **The status line stopped over-claiming.** It now reads `Plugin: <spec>  (/goal command wired; tui.json: written|skipped)`, and every cache removal is printed.

## Update instructions

### 1. Update the host first

From your host `llm-ferry` repository:

```bash
git pull --ff-only
ferry update --host
```

This rebuilds the global `ferry` binary, relinks it, and updates local OpenCode profiles (`~/.config/ferry/opencode-*.json` and the default `opencode.json`). The goal plugin is migrated, the dead cache directories go, and the pre-install runs — watch for the `Plugin: installed …` line.

### 2. Update each client

On each client laptop:

```bash
ferry update --client
```

### 3. Verify

```bash
find "${XDG_CACHE_HOME:-$HOME/.cache}/opencode/packages" \
  -path '*/node_modules/opencode-goal-plugin/package.json' -exec grep -m1 '"version"' {} +
```

Expect `"version": "0.10.1"`. Use `find`, not a glob: a spec's slashes become directories, so the tarball form lands eight levels down at `packages/opencode-goal-plugin@https:/github.com/sblattj/OpenCode-goal-plugin/archive/refs/tags/v0.10.1.tar.gz/`, and a single-level `packages/*opencode-goal-plugin*/…` pattern reports a healthy install as missing.

Then start OpenCode once and confirm both halves: `/goal` appears in the slash-command menu (server half) and the goal panel appears in the sidebar (TUI half, from `tui.json`).
