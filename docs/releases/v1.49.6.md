# llm-ferry v1.49.6: ferry msg and ferry log say when the host's share server is down

`ferry msg` and `ferry log` used to run a bare `curl`. When the host's share server was down, a client saw curl's "Couldn't connect to server" with no hint of what to do, and when the server answered with an error the command still exited 0, so a lost message looked sent.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/main/README.md)

## Fixed

- **A down share server is named, with the fix.** When nothing is listening on the share port, both commands print the URL, say the message was NOT sent, tell you to run `ferry share` on the host, and exit 1.
- **Every other failure exits 1 too, with its reason:** an unresolvable host name, no answer within 10 s, a profile with no `host`, or an HTTP error from the server (the message was NOT saved; check the host's share log).
- **`ferry msg` sends a leading `@` literally.** curl reads a body that starts with `@` as a file name, so `ferry msg @notes.txt` used to send the file's contents. The text now goes through stdin, exactly as typed.

## Tests

- `lib/ferry-share.test.py` gains `TestClientHqSend`: the real built `ferry` against the real embedded share server, covering a live send, a dead port, a real 500, a leading `@`, and a profile without a host.
