# llm-ferry v1.32.1 — The Download Proxy Stops Dropping Big Files

`ferry serve-proxy`'s HTTPS `CONNECT` tunnel now applies backpressure. Before this release a large download routed through it from a slower client died after about 1 MB.

[Read the project overview](https://github.com/sblattj/llm-ferry/blob/v1.32.1/README.md)

## What broke

A client running `eval "$(ferry env --host <host>)"` and then pulling `mlx-community/whisper-large-v3-turbo` through `huggingface_hub` saw:

```
Error while downloading from https://huggingface.co/.../weights.safetensors:
peer closed connection without sending complete message body
(received 1372170 bytes, expected 1613977612)
```

Both proxies answered, the small files arrived, and only the 1.6 GB weights file failed, every time, at roughly the same byte count.

## Why

The tunnel in `lib/ferry-proxy.zsh` set both sockets non-blocking and then relayed with `sendall()`. On a non-blocking socket `sendall()` raises `BlockingIOError` (EAGAIN) the moment the receiving side's buffer is full. The Hugging Face CDN fills a LAN client's receive buffer in well under a second, so the first time the client fell behind the relay raised, the bare `except` swallowed it, the `finally` closed the upstream socket, and the client saw the peer hang up. The received byte count is the size of the buffers between the two sockets, which is why it was stable run to run.

Reproduced outside ferry with a 20 MB upstream and a client that waits one second before reading: the old tunnel delivered 319 KB and reset the upstream.

## What changed

- **Blocking relay.** The tunnel keeps both sockets blocking. `select()` still decides which side has bytes; `sendall()` now blocks until the other side has taken them, and that blocking is the backpressure. A fast upstream simply waits for the client.
- **Half-close instead of hang-up.** EOF on one side now shuts down the write half of the other side and keeps relaying the reverse direction until it also finishes, so a reply sent after the request body's EOF still arrives. The old loop returned on the first EOF from either side.
- **Idle timeout 60 s → 300 s.** A tunnel with no bytes in either direction for five minutes is closed, up from one; a slow resolve step on a busy CDN no longer looks like an abandoned connection.
- **Tests.** New `lib/ferry-proxy.test.py` lifts the proxy heredoc out of the shell file and runs the real handler: a fast-upstream/slow-client case that must deliver every one of 20 MB, an upload-then-half-close case, and the 502 for an unreachable upstream. The first two fail on the v1.32.0 tunnel and pass here.

## Operator note

The proxy is a long-running Python process started by `ferry serve-proxy`, so a host that is already serving keeps running the old tunnel until it is restarted: `ferry down` then `ferry serve-proxy` on the host after updating (`ferry up` does not start the proxy).
